Topic 2.1

Definition & Objectives of Testing

Software Testing is the process of evaluating and verifying that a software product or application does what it is supposed to do. It involves executing a system or application to find any gaps, errors, or missing requirements that contradict the actual requirements.
📌 Last Night Tip
Remember testing is NOT about proving software works perfectly — it is about finding defects and building confidence in quality. The goal is to find failures, not prove their absence.

Standard Definitions

IEEE Definition

"Testing is the process of exercising or evaluating a system or system component by manual or automated means to verify that it satisfies specified requirements or to identify differences between expected and actual results."

ISTQB Definition

"Testing is the process consisting of all life cycle activities, both static and dynamic, concerned with planning, preparation, and evaluation of software products and related work products to determine that they satisfy specified requirements, to demonstrate that they are fit for purpose, and to detect defects."

Primary Objectives of Software Testing

🎯

Find Defects

Identify bugs, errors, and issues in the software before it reaches end users. Early detection reduces cost and effort significantly.

✅

Verify Requirements

Ensure the software meets all specified functional and non-functional requirements as documented.

🚫

Prevent Defects

Through static testing (reviews, inspections) catch defects before they become code-level issues.

📊

Build Confidence

Provide stakeholders evidence that the software quality is acceptable for release.

⚠️

Assess Risks

Identify areas of the software that pose the highest risk to business operations.

📋

Prevent Escapes

Stop defects from escaping into production where they cause real-world damage.

Testing vs. Quality Assurance — Key Distinction

Simple Analogy
Testing is like a doctor diagnosing an illness — they run tests to find what is wrong. Quality Assurance is like eating healthy and exercising — it prevents illnesses from occurring in the first place.

Topic 2.2

Role of Testing and its Effect on Quality

Testing plays a critical role in software quality by providing objective information about the current state of the software product. It directly impacts quality by identifying defects, measuring quality attributes, and providing feedback for improvement.

The Multiple Roles of Testing

1. Information Provider Role

Testing provides stakeholders with factual data about software quality — what works, what doesn't, and what risks remain. This enables informed release decisions.

2. Quality Gatekeeper Role

Testing acts as a checkpoint before software moves to the next phase or to production. If critical tests fail, the software cannot progress until issues are resolved.

3. Risk Mitigation Role

Testing identifies high-risk areas of the software, allowing teams to prioritize fixes and allocate resources where they matter most.

4. Feedback Role

Testing provides immediate feedback to developers about code quality, helping them improve their practices and learn from mistakes.

Topic 2.3

Causes of Software Failure: Error, Bug, Fault, Defect, Failure

Understanding the terminology of software failures is essential. These terms describe a chain of events from human mistake to system failure. The chain is: Error → Bug/Fault → Defect → Failure.
📌 Exam Tip
This is a direct 5-mark question: "Define and differentiate between Error, Bug, Fault, Defect, and Failure with examples." Learn the chain and one example for each.

The Complete Chain of Software Failure

Fig 2.3 — From Human Error to System Failure: The Defect Chain

Detailed Definitions with Examples

⚠️ ERROR

Definition: A human action that produces an incorrect result. An error is made by a person — developer, tester, analyst, or user.

Example: A developer writes if (x = 5) instead of if (x == 5) — this is an error (mistake) made by the human.

Key Point: Errors occur in the human mind before any code is written.

🐛 BUG / FAULT

Definition: The manifestation of an error in the software artifact. A bug is the actual incorrect code, design, or data.

Example: The incorrect code if (x = 5) saved in the source file is the bug/fault.

Key Point: Bugs are present in the software but may not cause visible failures until specific conditions are met.

📝 DEFECT

Definition: Any variation between actual and expected results. A broader term often used to refer to any problem requiring resolution.

Example: When a tester reports that "the login page accepts any password," this reported issue is a defect.

Key Point: A defect is the formal record of a problem in the defect tracking system.

💥 FAILURE

Definition: The deviation of the software from its expected behavior during execution.

Example: The login page actually letting a user in with wrong password — this observable incorrect behavior is a failure.

Key Point: Not every fault causes a failure. The fault must be executed under specific conditions to cause a failure.

Complete Example: Following the Chain

Complete Example — Banking Application
  1. ERROR: Developer incorrectly writes if (balance - amount < minimum_balance) instead of if (balance - amount < 0) — a human mistake.
  2. BUG/FAULT: The incorrect condition exists in the withdrawal function code.
  3. DEFECT: Tester discovers the issue and logs it as "DEFECT-401: Withdrawal allowed below zero when minimum balance feature is off."
  4. FAILURE: When a user with ₹500 tries to withdraw ₹700, the system incorrectly allows the transaction (because the bug condition was executed).
  5. INCIDENT: The customer's account goes negative, causing a bank charge and customer complaint.

Important Relationships to Remember

  • Not all faults cause failures — the fault may be in code that is never executed
  • A single fault can cause multiple failures — a null pointer check missing can crash many different functions
  • Multiple faults can cause a single failure — interaction of several bugs leads to one observable problem
  • Errors cause faults, faults may cause failures under certain conditions
⚠️ Common Confusion
Many textbooks use "bug" and "defect" interchangeably. In industry, "defect" is the formal tracked item, while "bug" is the technical flaw. For your exam, understand the distinction but don't overcomplicate — the chain is what matters.

Topic 2.4

Economics of Testing

The Economics of Testing refers to the cost-benefit analysis of testing activities. It recognizes that testing has costs (time, resources, tools) but provides value (defect prevention, quality assurance, risk reduction). The goal is to optimize testing investment to maximize returns.

The Cost of Finding Defects Early (The 1-10-100 Rule)

This is the most important economic principle in testing: the earlier a defect is found, the cheaper it is to fix.

💰 1-10-100 RULE: $1 to find/fix in requirements | $10 in design | $100 in coding | $1000+ in production
Fig 2.4 — Cost to Fix a Defect by Phase Detected

Why Does Cost Escalate So Dramatically?

  • Rediscovery cost: Time spent finding the defect again
  • Communication cost: Explaining the defect across teams
  • Regression cost: Retesting everything that might be affected
  • Deployment cost: Creating and distributing patches
  • Customer damage cost: Lost trust, support calls, SLA penalties
  • Opportunity cost: Developer time taken from new features

The Law of Diminishing Returns in Testing

There is an optimal point where additional testing yields progressively less value. Beyond this point, testing becomes economically inefficient.

Fig 2.5 — Diminishing Returns in Testing Investment

Testing Economics Decisions

What to Test More?

  • High-risk functionality (financial, safety-critical)
  • Frequently used features
  • Complex modules with many dependencies
  • Areas with history of many defects
  • Newly developed or recently changed code

What to Test Less?

  • Low-risk, low-impact features
  • Stable code with no recent changes
  • Third-party components with good reputation
  • Features being removed in next release
  • Cosmetic/UI elements with low business value
🌍 Real-World Economic Impact
NHS WannaCry Attack (2017): A known vulnerability (MS17-010) had a patch available for 2 months before the attack. Inadequate testing and deployment procedures meant the patch was never applied. The economic impact: £92 million in direct costs, 19,000 cancelled appointments, and immeasurable reputational damage. The fix cost $0 (patch was free). The failure cost: £92 million+.

Topic 2.5

Seven Testing Principles (ISTQB)

The Seven Testing Principles are fundamental guidelines that apply to all forms of software testing. They represent decades of collective experience and wisdom from the testing community.
📌 Exam Tip
Memorize all 7 principles. For each, know: (1) what it means in simple words, (2) one example. This is a guaranteed question — often 5-7 marks.
1️⃣

Testing shows presence of defects

Meaning: Testing can prove that defects exist, but cannot prove that defects do not exist. Even extensive testing cannot guarantee 100% defect-free software.

Example: You test an e-commerce checkout 100 times and it works perfectly. The 101st transaction with a specific combination of items and discount codes might still fail.

2️⃣

Exhaustive testing is impossible

Meaning: Testing everything (all inputs, all scenarios, all configurations) is impossible except for trivial cases. Testing must use risk-based prioritization.

Example: A login screen with username (unlimited combinations) and password (unlimited) — you cannot test every possible input. You test boundary values and common scenarios instead.

3️⃣

Early testing saves time and money

Meaning: Testing activities should start as early as possible in the software development life cycle. Find defects when they are cheapest to fix.

Example: Reviewing requirements before coding begins can catch ambiguous or missing requirements that would cost 100x more to fix after development.

4️⃣

Defects cluster together

Meaning: The Pareto Principle (80/20 rule) applies to software defects — approximately 80% of defects are found in about 20% of the modules.

Example: In an ERP system, the inventory management module may have 50 defects while the reporting module has only 2. Focus testing on the defect-prone areas.

5️⃣

Pesticide paradox

Meaning: If you run the same tests repeatedly, they will eventually stop finding new defects. Tests must be regularly reviewed and updated.

Example: Your regression test suite of 500 tests has passed 20 times without failures. It's time to analyze if these tests are still valuable or need to be enhanced.

6️⃣

Testing is context dependent

Meaning: Different contexts require different testing approaches. Testing a medical device is not the same as testing an e-commerce website.

Example: Safety-critical aviation software requires rigorous formal verification and exhaustive testing, while a mobile game might use exploratory testing and rapid feedback.

7️⃣

Absence-of-errors fallacy

Meaning: Finding and fixing many defects does not guarantee the software is useful or will satisfy customer needs. The software could be technically correct but still fail to meet business objectives.

Example: A banking app works perfectly (no technical defects) but has a confusing interface that makes customers unable to complete transactions — the software fails despite having no bugs.

Real Project Example — STLC in Action

Project: Adding "Buy Now" button to an e-commerce app

  • Phase 1: Analyze requirements — button must be visible only for logged-in users, with stock available
  • Phase 2: Plan — 2 testers, 3 days effort, regression impact on checkout flow
  • Phase 3: Write 15 test cases covering login, stock validation, payment integration
  • Phase 4: Set up staging environment with test payment gateway

Topic 2.7

Validation & Verification — V-Model and W-Model

Verification asks "Are we building the product right?" (static checking). Validation asks "Are we building the right product?" (dynamic checking). The V-Model and W-Model are process models that integrate testing with development phases.
📌 Last Night Tip
Remember: Verification = reviews, inspections, walkthroughs (no execution). Validation = actual testing with execution. "Verification checks documents, Validation tests the working software."

Verification vs Validation — The Critical Distinction

✓ VERIFICATION

Question: "Are we building the product correctly?"

Activity: Static testing — reviews, walkthroughs, inspections

Object: Requirements, design, code, documents

Timing: Before coding completes

Methods: Peer reviews, formal inspections, static analysis

Example: Reviewing the login requirement document to ensure it specifies password rules correctly

✗ VALIDATION

Question: "Are we building the correct product?"

Activity: Dynamic testing — executing the software

Object: Working software/application

Timing: After code is ready to execute

Methods: Functional testing, system testing, UAT

Example: Actually entering wrong passwords 3 times and verifying account locks

The V-Model (Verification and Validation Model)

The V-Model demonstrates the relationship between each development phase and its corresponding testing phase. The left side represents verification (static testing), and the right side represents validation (dynamic testing).

Fig 2.7 — The V-Model of Testing

V-Model Mappings (Verification → Validation)

  • Requirements → UAT: Does the system meet business needs?
  • System Design → System Testing: Does the complete system work as designed?
  • Architecture → Integration Testing: Do modules work together correctly?
  • Module Design → Unit Testing: Does each component work individually?

The W-Model (Dual V-Model)

The W-Model extends the V-Model by emphasizing that testing activities should occur in parallel with development activities — not just after them. It shows testing and development as two parallel tracks.

Fig 2.8 — The W-Model: Testing in Parallel with Development

V-Model vs W-Model Comparison

AspectV-ModelW-Model
Testing ApproachTesting happens after development phaseTesting happens in parallel with development
Timing of Test PlanningTest planning starts after requirements are completeTest planning begins simultaneously with development planning
Static TestingPresent but less emphasizedStrongly emphasized through reviews at each phase
Defect DetectionDefects found later in the cycleDefects found earlier due to parallel reviews
Best ForSmall to medium projects with clear requirements Complex projects requiring early defect detection
Simple Analogy — Building Construction

Verification: Reviewing the building blueprint before construction begins. Checking that all measurements are correct on paper.

Validation: Actually measuring the completed room to ensure it is 10x10 feet as specified.

V-Model: Finish the entire blueprint, then start building, then test at the end.

W-Model: Review each floor's blueprint, build that floor, test that floor, then move to next floor.

Topic 2.8

Agile Testing — Test Driven Development (TDD)

Test Driven Development (TDD) is a software development approach where tests are written before the code. The developer follows a short, repetitive cycle: write a failing test, write just enough code to pass the test, then refactor the code to improve its structure.
📌 Exam Tip
TDD is often called "Red-Green-Refactor" — remember the three steps in order. This is a favorite exam question: "Explain TDD with the red-green-refactor cycle."

The TDD Cycle — Red-Green-Refactor

Fig 2.9 — Test Driven Development (TDD) Red-Green-Refactor Cycle

Detailed Explanation of Each Phase

🔴 RED — Write a Failing Test

What happens: Before writing any production code, the developer writes a test for a small piece of functionality that does not yet exist.

Result: The test fails (red) because the code being tested hasn't been written yet.

Example: Writing a test that expects a `calculateDiscount(price, customerType)` function to return 10% off for premium customers — before writing the function itself.

🟢 GREEN — Make the Test Pass

What happens: Write the simplest possible code that makes the test pass. Do not add extra functionality.

Result: The test passes (green). All tests in the suite should now pass.

Example: Writing `if customerType == "premium": return price * 0.9` — nothing more, nothing less.

♻️ REFACTOR — Improve the Code

What happens: Clean up the code — remove duplication, improve naming, optimize structure — while keeping all tests passing.

Result: Better code quality with the same correct behavior.

Example: Extracting the discount logic into a separate helper function, adding constants for discount percentages.

Traditional Testing vs TDD

AspectTraditional DevelopmentTest Driven Development (TDD)
OrderWrite code → Write tests → Debug Write tests → Write code → Refactor
Test Purpose Verify existing code works Drive the design and implementation
Confidence Level Moderate — tests may be incomplete High — every line has a test behind it
Debugging Time High — defects found late Low — defects found immediately when introduced

Example: TDD in Action — Calculating Age from Birthdate

Complete TDD Example

Requirement: Function should calculate a person's age in years given their birthdate.

🔴 RED: Write test first

def test_calculate_age():
    birthdate = "1990-05-15"
    today = "2024-05-15"
    result = calculate_age(birthdate, today)
    assert result == 34    # This test will FAIL — function doesn't exist yet

🟢 GREEN: Write minimum code

def calculate_age(birthdate, today):
    return 34    # Hardcoded — makes the test pass but not real solution

♻️ REFACTOR: Replace with real calculation

def calculate_age(birthdate, today):
    birth = datetime.strptime(birthdate, "%Y-%m-%d")
    today_dt = datetime.strptime(today, "%Y-%m-%d")
    age = today_dt.year - birth.year
    if today_dt.month < birth.month or (today_dt.month == birth.month and today_dt.day < birth.day):
        age -= 1
    return age    # Now add more test cases (birthdays, leap years, etc.)

Benefits of TDD

  • Higher test coverage: Every line of code is written to pass a test
  • Better design: Testable code tends to be better designed (loose coupling, high cohesion)
  • Immediate feedback: Developers know within seconds if they broke something
  • Regression safety: The test suite grows with the codebase, catching regressions instantly
  • Living documentation: Tests describe how the code should behave
  • Reduced debugging time: Defects are caught when they are introduced, not weeks later
⚠️ Common TDD Mistakes
  • Writing too large a test — tests should be small (one assertion per test)
  • Skipping the refactor step — this is where long-term quality comes from
  • Writing tests after the code — that's not TDD, that's just "adding tests"
  • Writing tests that are too complex — tests should be simple and focused

Topic 2.9

Levels of Testing

Testing is performed at multiple levels throughout the software development life cycle. Each level has a specific focus, scope, and objective. The levels form a hierarchy from testing small components to testing the complete system.
📌 Last Night Tip
Remember the pyramid: Unit (many small tests) → Integration → System → UAT (few large tests). Each level has distinct objectives and stakeholders.
Fig 2.10 — The Testing Levels Pyramid

The pyramid principle: Write many fast, small unit tests at the bottom, fewer slower end-to-end tests at the top.

Detailed Explanation of Each Level

2.9.1 — Unit (Component) Testing

Definition: Testing of individual software components or modules in isolation. Typically performed by developers using test frameworks (JUnit, pytest, NUnit).

  • Scope: Single function, method, or class
  • Objective: Verify that each unit performs as designed
  • Who performs: Developers
  • When: During coding phase
  • Example: Testing that a `validateEmail(email)` function correctly identifies valid email formats

2.9.2 — Integration Testing

Definition: Testing the interactions and interfaces between integrated components to detect interface defects.

  • Scope: Two or more units working together
  • Objective: Verify that components work correctly when combined
  • Who performs: Developers or testers
  • When: After unit testing, before system testing
  • Example: Testing that the `validateEmail` function's output is correctly used by the `registerUser` function
🌍 Integration Testing Failure Example
NASA Mars Climate Orbiter (1999): The spacecraft was lost because one team used metric units (newton-seconds) and another used imperial units (pound-seconds). Both units worked perfectly in isolation. The integration testing failed to catch the unit mismatch. Cost: $125 million loss.

2.9.3 — System Testing

Definition: Testing the complete, integrated application to evaluate compliance with specified requirements.

  • Scope: Entire system as a whole
  • Objective: Verify end-to-end system behavior against requirements
  • Who performs: Independent test team
  • When: After integration testing, before UAT
  • Example: Testing the complete e-commerce flow: login → search → add to cart → checkout → payment → confirmation

2.9.4 — User Acceptance Testing (UAT)

Definition: Testing performed by end-users to determine whether the software meets their business needs and is ready for production deployment.

  • Scope: Business workflows from user perspective
  • Objective: Validate that the software solves real business problems
  • Who performs: End users, business analysts, product owners
  • When: After system testing, before production release
  • Example: Hospital nurses testing a new patient admission system using real patient scenarios

Topic 2.10

Test Types

Test Types classify tests based on the objective of testing — what you are trying to evaluate. While test levels (Unit, Integration, System) define when you test, test types define what aspect you are testing.
📌 Exam Tip
Distinguish between test LEVELS (scope/when) and test TYPES (objective/what). Levels are about size and integration; types are about functionality vs structure vs non-functional properties.

The Three Main Test Type Categories

⚫

Functional Testing (Black-Box)

Tests WHAT the system does. Focuses on requirements and expected behavior without looking at internal code structure.

Example: Entering username "john" and password "pass123" — does login succeed?

⬜

Structural Testing (White-Box)

Tests HOW the system works. Examines internal code structure, logic paths, and implementation details.

Example: Testing all branches of an if-else statement, ensuring every line of code executes.

📊

Non-Functional Testing

Tests HOW WELL the system performs under various conditions. Covers performance, usability, security, reliability, etc.

Example: Can 10,000 users login simultaneously without slowing down?

2.10.1 — Functional Testing (Black-Box)

Definition: Testing based on requirements and specifications without knowledge of internal code structure. The tester treats the system as a "black box" — inputs go in, outputs come out, internal workings are not examined.

Functional Testing Techniques:

  • Equivalence Partitioning: Divide input data into groups that should behave similarly. Test one value from each group.
  • Boundary Value Analysis: Test values at the edges of valid ranges (minimum, maximum, just inside, just outside).
  • Decision Table Testing: Create tables showing combinations of conditions and expected actions.
  • State Transition Testing: Test how the system behaves when moving between different states.
  • Use Case Testing: Test end-to-end business scenarios from user perspective.
Functional Testing Example — ATM Withdrawal

Requirement: ATM allows withdrawal between ₹100 and ₹20,000 in multiples of ₹100.

  • Equivalence Partitioning: Valid: ₹500, ₹5,000, ₹15,000 | Invalid: ₹50, ₹25,000, ₹0
  • Boundary Value Analysis: Test ₹100 (min), ₹99 (min-1), ₹101 (min+1), ₹20,000 (max), ₹19,999 (max-1), ₹20,001 (max+1)

2.10.2 — Non-Functional Testing (Product Characteristics)

Definition: Testing the quality attributes of the software — how well it performs, how easy it is to use, how secure it is, how reliable it operates under load.

(Detailed coverage of Non-Functional Testing types is in Topic 2.11)

2.10.3 — Structural Testing (White-Box)

Definition: Testing based on knowledge of the internal code structure. The tester designs tests to execute specific paths, branches, or conditions within the code.

White-Box Testing Coverage Levels:

  • Statement Coverage: Every line of code executed at least once
  • Branch Coverage: Every branch (if/else, switch case) taken in both true and false directions
  • Path Coverage: Every possible path through the code executed (often impractical for complex code)
  • Condition Coverage: Every Boolean sub-expression evaluated both true and false
Fig 2.11 — Black-Box vs White-Box Testing Perspective

2.10.4 — Testing Related to Changes: Confirmation and Regression Testing

✓ Confirmation Testing (Re-testing)

Definition: Running a test that previously failed after a fix has been made, to confirm the defect is actually resolved.

When to perform: After developer provides a fix for a reported defect

Scope: Only the specific test case(s) that failed originally

Example: Defect: "Login fails with correct credentials". Developer fixes the issue. Tester re-runs the exact login test to confirm it now works.

🔄 Regression Testing

Definition: Running a set of tests to ensure that new code changes have not broken existing functionality.

When to perform: After any code change — bug fix, new feature, configuration change, refactoring

Scope: A suite of tests covering core functionality that should not be affected

Example: After fixing the login bug, the tester runs all 500 existing tests to ensure nothing else broke.

Confirmation vs Regression — Real Scenario

Situation: E-commerce site has 10,000 tests. Test #487 (checkout with credit card) fails.

Step 1: Developer fixes the checkout code.

Step 2 — Confirmation Testing: Tester re-runs only Test #487. It passes. The specific defect is confirmed fixed.

Step 3 — Regression Testing: Tester runs the entire suite of 10,000 tests to ensure the fix didn't break login, search, cart, or any other functionality. Three other tests fail — regression issues. Those must be fixed now.

Conclusion: Confirmation proves the specific fix worked. Regression proves nothing else was broken by the fix.

Topic 2.11

Non-Functional Testing Types

Non-functional testing verifies the quality attributes of software — how well it performs, how easy it is to use, how secure it is, and how reliably it operates. Unlike functional testing (which checks WHAT the system does), non-functional testing checks HOW WELL the system does it.
📌 Last Night Tip
For exams, remember the main non-functional types: Performance (Load + Stress), Usability, Maintainability, Portability, Security, and Localization/Internationalization. Each answers a specific "how well" question.

2.11.1 — Performance Testing (Load & Stress)

📈 Load Testing

Definition: Testing the system under expected normal and peak load conditions. Answers: "Does the system handle the expected number of users?"

Example: Simulating 1,000 concurrent users on an e-commerce site during a sale. Measuring response time stays under 2 seconds for 95% of transactions.

Metrics measured: Response time, throughput (transactions/sec), resource utilization (CPU, memory, network)

💥 Stress Testing

Definition: Testing the system beyond its expected capacity to find its breaking point and how it recovers. Answers: "What happens when traffic exceeds expectations? Does it crash gracefully?"

Example: Ramping up users from 1,000 to 10,000 to 50,000 to find where response time becomes unacceptable or the server crashes.

Metrics measured: Breaking point, failure behavior (graceful degradation vs crash), recovery time

2.11.2 — Usability Testing

Definition: Testing how easily end users can learn and use the software. Evaluates the user interface, navigation, and overall user experience (UX).

  • Objectives: Is the software intuitive? Can users complete tasks without training? Are error messages helpful?
  • Methods: User observation, task completion time measurement, satisfaction surveys, A/B testing
  • Example: Giving 5 new users a task: "Find and purchase a blue T-shirt in size Medium." Measure how long it takes and how many clicks are needed.
Usability Testing Example — Banking App

Task: Transfer money to a saved payee.

Success criteria: User completes task within 60 seconds without assistance.

Typical findings: "The 'Add Payee' button is hidden in a menu — users couldn't find it. We need to move it to the main screen."

2.11.3 — Maintainability Testing

Definition: Testing how easily the software can be modified to fix defects, add features, or adapt to changing environments.

  • Factors: Code readability, documentation quality, modularity, testability, tool support
  • Example: A new developer is asked to add a 10% discount for premium customers. How many hours does it take? How many existing tests break?

2.11.4 — Portability Testing

Definition: Testing the ease with which software can be transferred from one environment to another (different operating systems, browsers, devices, hardware configurations).

  • Example: Testing a web application on Windows + Chrome, Mac + Safari, Linux + Firefox, Android + Chrome, iOS + Safari, and verifying identical behavior.
  • Metrics: Percentage of environments where software works correctly, installation time, configuration complexity

2.11.5 — Security Testing

Definition: Testing the software's ability to protect data and maintain functionality against malicious attacks. (Detailed in Unit 1 and Unit 3)

  • Types of security testing: Vulnerability scanning, penetration testing, authentication testing, authorization testing, encryption testing
  • Example: Attempting SQL injection on login page (`' OR '1'='1` as password) to see if the database is exposed.

2.11.6 — Localization & Internationalization Testing

🌐 Internationalization (I18N)

Definition: Designing the software to be adaptable to different languages and regions without engineering changes.

What to test: Does the code support Unicode? Are date/time formats configurable? Can text expand for longer translations?

Example: The string "Submit" in English becomes "Submeter" in Portuguese (same length) but "Enviar" (shorter) — does the button resize correctly?

📍 Localization (L10N)

Definition: Adapting the software for a specific region or language, including translations, currency, date formats, and cultural conventions.

What to test: Translations are accurate, currency symbols are correct ($ vs € vs ¥), date format matches local preference (DD/MM/YYYY vs MM/DD/YYYY).

Example: In the US, date is 12/25/2024 (Christmas). In India, same date should display as 25/12/2024. Does the software handle this correctly?

Topic 2.12

Concept of Smoke Testing and Sanity Testing

Smoke Testing and Sanity Testing are two types of testing performed to quickly determine whether a build is stable enough for more detailed testing. They are often confused but have distinct purposes and scopes.
📌 Exam Tip
Remember: Smoke Testing = "Does the build even work?" (shallow and wide). Sanity Testing = "Does the specific fix work?" (deep but narrow). Both are subsets of regression testing.

Smoke Testing (Build Verification Testing)

Definition: A preliminary test conducted on a new software build to determine if it is stable enough to proceed with more rigorous testing. Smoke testing verifies the critical functionalities of the system.

Characteristics of Smoke Testing:

  • Scope: Broad but shallow — tests major functions without deep validation
  • Objective: Check if the build is "ready" for formal testing
  • When: Immediately after receiving a new build from development
  • Who: Usually performed by testers or automated CI/CD pipeline
  • Duration: Typically 10-30 minutes
  • Fail condition: If smoke test fails, the build is rejected and sent back to developers
Smoke Testing Example — E-commerce Application

Smoke Test Suite (10 tests covering core functionality):

  1. Can I access the homepage? (Verify site loads)
  2. Can I search for a product?
  3. Can I add a product to cart?
  4. Can I proceed to checkout?
  5. Can I enter shipping details?
  6. Can I enter payment information?
  7. Can I complete the order?
  8. Can a user log in?
  9. Can a user register?
  10. Can the admin access the dashboard?

If any of these 10 tests fail, the build is rejected. No point testing detailed features like "apply discount code" or "validate tax calculation" if the basic checkout flow is broken.

Sanity Testing

Definition: A focused test performed after receiving a build with minor changes (bug fixes) to verify that the specific fixes work and have not caused major issues in related areas.

Characteristics of Sanity Testing:

  • Scope: Narrow but deep — focuses only on the changed functionality and its immediate dependencies
  • Objective: Verify that a specific fix works and doesn't break nearby functionality
  • When: After smoke testing passes, before full regression testing
  • Who: Usually performed by testers
  • Duration: 10-30 minutes (similar to smoke, but different focus)
  • Fail condition: If sanity test fails, the fix is rejected
Sanity Testing Example — After a Specific Bug Fix

Bug fixed: "Discount code 'SAVE10' applies 5% instead of 10% discount."

Sanity Test Suite (5-10 tests focused on discount feature):

  1. Apply 'SAVE10' — Verify discount is exactly 10%
  2. Apply invalid code — Verify error message appears
  3. Apply expired code — Verify appropriate message
  4. Apply code after removing item — Verify discount recalculates
  5. Check that unrelated feature (shipping calculation) still works
  6. Check that checkout total is accurate with discount

If all pass, proceed to full regression testing on the whole application.

⚠️ Common Confusion
Many practitioners use "smoke testing" and "sanity testing" interchangeably — but they are different. For exam purposes, know the distinction. Smoke = "is the build fundamentally broken?" Sanity = "does this specific fix work?"
Unit 2 — Key Takeaway

Software testing is a vast discipline, but the fundamentals are consistent: understand the difference between verification and validation, master the testing levels (unit through UAT), apply the seven principles, know your test types (functional, non-functional, structural), and use smoke and sanity testing to efficiently manage build quality. Testing is not an afterthought — it is an integral part of software development that saves time, money, and reputations.
