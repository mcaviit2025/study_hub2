Topic 3.1

Static Techniques – Review

Static Review is a systematic examination of software artifacts (requirements documents, design specifications, code, test plans) by people to identify defects, omissions, and improvements — without executing the software.

3.1.1 — Review Process (Informal & Formal)

Review Process — General Steps

Fig 3.1 — General Review Process Flow

Types of Reviews: Formal vs Informal

📝 Informal Review

Definition: A lightweight review process with no formal documentation, roles, or strict procedures.

Characteristics:

  • No formal process or documentation
  • No defined roles (moderator, scribe, etc.)
  • Can be ad-hoc or pair-based
  • Quick and low-cost
  • Examples: Desk checking, pair programming review, colleague quick look

Best for: Early feedback on small changes, quick verification of simple documents

📋 Formal Review

Definition: A structured review process with defined roles, entry/exit criteria, metrics collection, and documented outputs.

Characteristics:

  • Follows defined process with checklists
  • Assigned roles (Moderator, Author, Reviewer, Scribe, Manager)
  • Quantitative metrics collected (defect density, preparation rate)
  • Formal reporting and follow-up
  • Examples: Formal Inspection (Fagan), Technical Review

Best for: Critical/safety-critical systems, regulatory compliance, formal certification

Comparison: Informal vs Formal Review

AspectInformal ReviewFormal Review
ProcessUndefined, flexibleDefined, strict
DocumentationMinimal or noneDetailed (checklists, logs, reports)
RolesNo formal rolesModerator, Author, Reviewer, Scribe
MetricsNot collectedDefect density, preparation rate, meeting efficiency
CostLowHigh (more time, more people)
ExamplesDesk checking, pair reviewFagan Inspection, Technical Review

3.1.2 — Technical or Peer Review

Technical Review (Peer Review) is a formal review conducted by technical peers (developers, testers, architects) to evaluate a software artifact. The focus is on identifying technical defects, deviations from specifications, and suggesting improvements.

Roles in Technical/Peer Review

  • Moderator: Plans and facilitates the review meeting
  • Author: Creator of the work product being reviewed
  • Reviewers: Technical peers who examine the work product
  • Scribe/Recorder: Documents defects and decisions
  • Manager: (Optional) Oversees process but does not participate technically

Technical Review Process Steps

  1. Planning: Select moderator, identify reviewers, schedule meeting, distribute documents
  2. Kick-off: Brief reviewers on scope, objectives, and any special focus areas
  3. Individual Preparation: Each reviewer examines the work product independently
  4. Review Meeting: Team discusses findings, identifies defects, suggests solutions
  5. Rework: Author fixes identified defects
  6. Follow-up: Moderator verifies fixes are complete and correct
Technical Review Example

Context: A developer has written a new sorting algorithm module.

Review Team: Moderator (Team Lead), Author (Developer), 2 Senior Developers as Reviewers, Scribe

Findings in Review:

  • Algorithm has O(n²) worst-case complexity — suggest using quicksort instead
  • Missing null pointer check before accessing array
  • Variable naming inconsistent with team standards
  • Missing comments for complex recursion logic

Outcome: 4 defects identified, fixed within 2 days, re-reviewed and accepted.

3.1.3 — Walkthrough

Walkthrough is a form of review where the author leads the participants through the work product step-by-step to gather feedback, understand the content, and identify defects. It is less formal than an inspection but more structured than informal review.

Characteristics of Walkthrough

  • Led by Author: The author presents and walks through the work product
  • Educational Component: Helps participants understand the product
  • Moderately Structured: More formal than informal review, less than inspection
  • Scenarios Used: Often uses test cases or usage scenarios to simulate execution
  • Documentation: Minutes or defect log may be kept
Walkthrough Example — Requirements Document

Scenario: Requirements document for a new ATM withdrawal feature.

Process: Business Analyst walks through each requirement line-by-line while developers and testers ask questions:

  • "What happens if the user requests amount exceeding daily limit?"
  • "How does the system behave if the ATM has insufficient cash?"
  • "What is the expected response time for balance check?"

Outcome: 12 ambiguities identified and clarified. Updated requirements document after walkthrough.

3.1.4 — Inspection

Inspection is the most formal type of review, originally defined by Michael Fagan at IBM. It follows a rigorous, metrics-based process with well-defined roles, checklists, entry/exit criteria, and quantitative goals.
📌 Exam Tip
Inspection is the most formal review technique. Remember: Fagan Inspection — Moderator (not author) leads, formal metrics collected, checklists used, entry/exit criteria defined.

Fagan Inspection — Key Characteristics

  • Moderator-led: Author does NOT lead (distinguishes from walkthrough)
  • Quantitative Metrics: Defect density, preparation rate, inspection rate, rework effort
  • Checklist-based: Reviewers use structured checklists (common defect types)
  • Entry Criteria: Work product must meet quality thresholds before inspection
  • Exit Criteria: Must pass defect density thresholds to exit
  • Separate Stages: Overview, Preparation, Inspection Meeting, Rework, Follow-up

Topic 3.2

Static Techniques – Static Analysis

Static Analysis is the automated analysis of source code without executing the program. Static analysis tools examine code to find potential defects, security vulnerabilities, coding standard violations, and structural anomalies.
📌 Exam Tip
Static analysis is automated (done by tools) vs reviews which are manual (done by people). Both are static testing because no code execution happens.

3.2.1 — Static Analysis by Tools (Automated Static Analysis)

What Static Analysis Tools Can Find

  • Syntax Errors: Code that violates language grammar rules
  • Semantic Errors: Valid syntax but wrong meaning (e.g., assignment in condition: `if (x = 5)` instead of `if (x == 5)`)
  • Code Standards Violations: Naming conventions, indentation, documentation requirements
  • Security Vulnerabilities: Buffer overflows, SQL injection patterns, hardcoded passwords
  • Potential Runtime Errors: Null pointer dereferences, array index out of bounds, division by zero
  • Code Complexity Metrics: Cyclomatic complexity, nesting depth, code duplication
  • Dead/Unreachable Code: Code that can never be executed
  • Resource Leaks: Files, database connections, memory not released

Popular Static Analysis Tools

Static Analysis Example — Tool Output

Code snippet (Java):

public String getName(User user) {
    String name = null;
    if (user != null) {
        name = user.getName();
    }
    return name.toUpperCase();  // Potential null pointer!
}

Static Analysis Tool Report (SpotBugs):

  • NP_ALWAYS_NULL: "name is always null when user is null. Dereference of name.toUpperCase() will throw NullPointerException."
  • Severity: High | Category: Correctness
  • Suggestion: Add null check before calling toUpperCase() or return null/empty string.

Benefits of Static Analysis

  • Early Defect Detection: Find defects before dynamic testing begins
  • Low Cost: Automated tools run in minutes vs hours of manual review
  • Consistent Enforcement: Tools apply rules uniformly across entire codebase
  • Integration with CI/CD: Can run automatically on every code commit
  • Security Vulnerability Discovery: Find patterns that human reviewers might miss
  • Code Quality Metrics: Quantitative data for technical debt management
⚠️ Limitations of Static Analysis
  • False Positives: Tools report defects that are not actual problems — requires human review
  • False Negatives: Tools may miss certain types of defects
  • Cannot Test Timing/Performance: No execution means no timing or performance analysis
  • Requires Configuration: Need to customize rules for project context
References
  • Ayewah, N. et al. — Using Static Analysis to Find Bugs, IEEE Software
  • SonarQube Documentation: https://www.sonarqube.org
  • OWASP — Source Code Analysis Tools
Topic 3.3

Black Box Testing Techniques

Black Box Testing (also called Specification-based Testing) designs test cases based solely on the specification of the software — without knowledge of internal code structure. The tester inputs data and observes outputs without knowing how the system processed the input.
📌 Last Night Tip
Black Box techniques are about WHAT the system does, not HOW. The four key techniques: Equivalence Partitioning, Boundary Value Analysis, Decision Table Testing, State Transition Testing.

3.3.1 — Equivalence Partitioning

Definition: A technique that divides input data into groups (partitions) where all values in a partition should be treated the same way by the software. Test only one value from each partition — if that works, all values in that partition should work.

Fig 3.3 — Equivalence Partitioning Example
Equivalence Partitioning Example

Requirement: A system accepts age input between 18 and 60 (inclusive).

Partitions:

  • Valid Partition: 18 to 60 — test with one value (e.g., 30)
  • Invalid Partition (below): Less than 18 — test with one value (e.g., 15)
  • Invalid Partition (above): Greater than 60 — test with one value (e.g., 75)

Result: Instead of testing all 43 possible ages, test only 3 values — reduces test cases by 93%.

3.3.2 — Boundary Value Analysis (BVA)

Definition: A technique that focuses on testing values at the boundaries between partitions. Most defects occur at boundaries, so we test minimum, maximum, and values just inside and just outside boundaries.

Boundary Value Analysis Example

Requirement: Age between 18 and 60 inclusive.

Boundary Values to Test:

  • 17 (just below lower boundary)
  • 18 (lower boundary)
  • 19 (just above lower boundary)
  • 59 (just below upper boundary)
  • 60 (upper boundary)
  • 61 (just above upper boundary)

Why 6 values? We test both boundaries with 3 values each (boundary -1, boundary, boundary +1).

Equivalence Partitioning + Boundary Value Analysis = Powerful Combination

Fig 3.4 — EP + BVA Combined Testing

3.3.3 — Decision Table Testing

Definition: A technique that uses a table to show combinations of conditions and their corresponding actions. Decision tables are particularly useful for business rules with complex logical conditions.

Decision Table Example — Loan Approval

Conditions:

  • C1: Credit Score ≥ 700
  • C2: Monthly Income ≥ ₹50,000
  • C3: Existing Loan (Yes/No)

Actions: Approve Loan, Reject Loan, Refer to Manager

RuleR1R2R3R4R5R6R7R8
C1 (Credit ≥ 700)TTTTFFFF
C2 (Income ≥ 50k)TTFFTTFF
C3 (Has Loan)TFTFTFTF
ActionReferApproveRejectApproveReferReferRejectReject

Test Cases: One test case for each column (8 test cases covering all combinations).

When to Use Decision Table Testing

  • Business rules with multiple conditions
  • Complex logical conditions (AND, OR, NOT combinations)
  • When different condition combinations lead to different actions
  • To ensure complete coverage of all possible scenarios

3.3.4 — State Transition Testing

Definition: A technique that models a system as a finite set of states, transitions between states triggered by events, and actions that occur on transitions. Test cases cover sequences of valid and invalid transitions.

Fig 3.5 — State Transition Diagram (ATM PIN Validation)
State Transition Test Cases — ATM PIN

Valid Sequence (Happy Path): Start → (insert card) → PIN Entry → (correct PIN) → Access Granted

Invalid Sequence 1 (Retry): Start → PIN Entry → (incorrect PIN) → PIN Entry → (incorrect PIN) → PIN Entry → (correct PIN) → Access Granted

Invalid Sequence 2 (Block): Start → PIN Entry → (incorrect PIN) → PIN Entry → (incorrect PIN) → PIN Entry → (incorrect PIN) → Card Blocked

Test Coverage Metrics:

  • 0-switch (state coverage): All states visited at least once
  • 1-switch (transition coverage): All transitions exercised
  • 2-switch: All sequences of two transitions tested

Topic 3.4

White Box Testing Techniques

White Box Testing (also called Structural Testing or Glass Box Testing) designs test cases based on the internal structure of the code. The tester has knowledge of the implementation and creates tests to exercise specific statements, branches, paths, or conditions.
📌 Exam Tip
White Box techniques are about HOW the system works internally. Key techniques: Statement Coverage, Branch/Decision Coverage, Path Coverage, Cyclomatic Complexity, Data Flow Testing, Mutation Testing. Understand the differences between coverage levels!

3.4.1 — Statement Coverage

Definition: The percentage of executable statements that have been executed by the test suite. Statement coverage = (Number of statements executed / Total number of statements) × 100%

Statement Coverage Example
1  int calculateDiscount(int price, boolean isPremium) {
2      int discount = 0;
3      if (isPremium) {
4          discount = price * 10 / 100;   // Statement A
5      } else {
6          discount = price * 5 / 100;    // Statement B
7      }
8      if (price > 1000) {
9          discount = discount + 50;       // Statement C
10     }
11     return discount;
12 }

Test Case 1: price = 500, isPremium = true
Executes lines: 1,2,3,4,8,9? (500 > 1000? false → skip line 9), 10,11,12
Statement Coverage = 10/11 = 91% (line 6 never executed, line 9 not executed)

Test Case 2: price = 1500, isPremium = false
Executes lines: 1,2,3,6,8,9,11,12
Combined: All 11 statements executed = 100% statement coverage

3.4.2 — Branch & Decision Coverage

Definition: Branch coverage requires that every possible branch (each outcome of a decision) is executed at least once. For an if statement, both true and false branches must be executed.

Fig 3.6 — Branch Coverage Example

Statement Coverage vs Branch Coverage

AspectStatement CoverageBranch/Decision Coverage
What it measuresLines of code executed Decision outcomes (true/false) executed
Weakness Can achieve 100% without executing all branches More thorough than statement coverage
Example missing if(x>0) { x++; } — testing x=5 gives 100% but x<=0 never tested Requires both x=5 and x=0 to achieve 100%
Relationship 100% Branch Coverage implies 100% Statement Coverage (but not vice versa)

3.4.3 — Path Coverage

Definition: Path coverage requires executing all possible paths through the code from entry to exit. A path is a unique sequence of branches from start to end.

⚠️ Path Coverage Limitation
For code with loops, the number of paths can be infinite or astronomically large (path explosion problem). Therefore, path coverage is often impractical for real systems — used primarily for small, critical modules.
Path Coverage Example
1  void process(int a, int b) {
2      if (a > 0) {        // Branch 1
3          a = a + 1;      // Statement
4      }
5      if (b > 0) {        // Branch 2
6          b = b - 1;      // Statement
7      }
8      return a + b;
9  }

Possible Paths (combinations of branches):

  • Path 1: Branch1-TRUE, Branch2-TRUE (a=5, b=5)
  • Path 2: Branch1-TRUE, Branch2-FALSE (a=5, b=-1)
  • Path 3: Branch1-FALSE, Branch2-TRUE (a=-1, b=5)
  • Path 4: Branch1-FALSE, Branch2-FALSE (a=-1, b=-1)

Path Coverage = 100% requires all 4 test cases. (Compare to Branch Coverage = 100% requires only 2 test cases covering both outcomes of each branch)

3.4.4 — McCabe's Cyclomatic Complexity Metric

Cyclomatic Complexity is a software metric developed by Thomas McCabe that measures the number of linearly independent paths through a program's source code. It provides a quantitative measure of code complexity and testability.
📌 Exam Tip — Formula to Memorize

Three ways to compute Cyclomatic Complexity (all give same result):

  • Method 1 (Edges - Nodes + 2): V(G) = E - N + 2
  • Method 2 (Decision nodes + 1): V(G) = D + 1 (where D = number of binary decision nodes)
  • Method 3 (Regions in flow graph): V(G) = Number of regions in the flow graph

Interpretation: V(G) = maximum number of test cases needed for branch coverage. V(G) ≤ 10 recommended for maintainable code.

Cyclomatic Complexity — Step by Step Computation Example

Computing Cyclomatic Complexity
1   int findMax(int a, int b, int c) {
2       int max;
3       if (a > b) {           // Decision 1
4           if (a > c) {       // Decision 2
5               max = a;
6           } else {
7               max = c;
8           }
9       } else {
10          if (b > c) {       // Decision 3
11              max = b;
12          } else {
13              max = c;
14          }
15      }
16      return max;
17  }

Flow Graph: Draw nodes for each statement, edges for flow of control.

Decision nodes (D): Lines 3, 4, 10 → D = 3

Method 2 (Easiest): V(G) = D + 1 = 3 + 1 = 4

Interpretation: Need at least 4 test cases to achieve branch coverage.

3.4.5 — Data Flow Based Testing

Definition: Data flow testing tracks the lifecycle of variables through the code — where they are defined (assigned a value), where they are used (read), and where they are undefined (killed/redefined).

Key Data Flow Concepts

  • Definition (def): A variable gets a value (e.g., `x = 5`, function parameter, input read)
  • Use (c-use / p-use): Variable is read — computational use (`y = x + 1`) or predicate use (`if (x > 0)`)
  • def-use pair: A definition and a subsequent use without redefinition in between
  • def-clear path: A path from definition to use with no redefinition of the same variable
Data Flow Testing Example
1   int calculate(int x, int y) {   // x and y are DEFINED (parameters)
2       int result;
3       if (x > 0) {                 // USE of x (p-use)
4           result = x * y;          // DEFINITION of result, USE of x and y (c-use)
5       } else {
6           result = 0;              // DEFINITION of result
7       }
8       return result;               // USE of result
9   }

Def-Use Pairs:

  • (x def at line 1, use at line 3)
  • (x def at line 1, use at line 4)
  • (y def at line 1, use at line 4)
  • (result def at line 4 or 6, use at line 8)

Data Flow Coverage Criteria (increasing thoroughness):

  1. All-defs: For each def, cover at least one def-use pair
  2. All-uses: For each def, cover all def-use pairs
  3. All-du-paths: Cover all paths between each def and use

3.4.6 — Mutation Testing

Mutation Testing is a fault-based testing technique that evaluates test quality by introducing small changes (mutations) to the program code and checking whether the test suite detects the change. A good test suite should "kill" (detect) most mutants.
📌 Exam Tip
Mutation Testing: Mutants are small syntactic changes (e.g., < changed to ≤, + changed to -, true changed to false). If tests pass with a mutant → the mutant "survived" → test suite is weak. Mutation Score = (Killed Mutants / Total Mutants) × 100%
Fig 3.8 — Mutation Testing Process Flow

Types of Mutations (Examples)

Mutation TypeOriginal CodeMutated Code
Arithmetic Operator`x = a + b``x = a - b`
Relational Operator`if (x > y)``if (x >= y)`
Logical Operator`if (a && b)``if (a || b)`
Constant Change`int max = 100``int max = 101`
Statement Deletion`x = y; z = x;``x = y;` (delete second)
Return Value`return result;``return null;`
True/False Flip`while (true) { }``while (false) { }`
Mutation Testing Example

Original Code: `if (age >= 18) { allowAccess(); }`

Mutant 1 (Relational): `if (age > 18) { allowAccess(); }`

Test: age = 18 → Original: allowAccess() called, Mutant: NOT called

Test Suite: Includes test with age=18 → This test FAILS on the mutant → Mutant KILLED ✓

Test Suite: Only tests age=20 → Both original and mutant behave the same → Mutant SURVIVED ✗ (Test suite is weak)

Benefits and Limitations of Mutation Testing

✓ Benefits

  • Highly effective at identifying test suite weaknesses
  • Objective measure of test quality
  • Finds subtle faults that other techniques miss
  • Forces creation of high-quality tests

✗ Limitations

  • Computationally expensive: Run tests for each mutant (100s or 1000s of executions)
  • Equivalent mutants: Some mutants are functionally equivalent to original — cannot be killed
  • High setup effort: Requires mutation testing tool

Topic 3.5

Experience Based Testing Techniques

Experience-based testing relies on the tester's knowledge, intuition, experience, and creativity to design test cases. These techniques are particularly effective for finding defects that systematic techniques might miss — especially edge cases, unusual scenarios, and real-world usage patterns.
📌 Last Night Tip
Experience-based techniques: Error Guessing (prediction of likely errors based on past experience) and Exploratory Testing (simultaneous learning, test design, and execution). Both rely on tester skill and domain knowledge.

3.5.1 — Error Guessing

Definition: Error guessing is an ad-hoc technique where the tester uses their experience, intuition, and knowledge of common software pitfalls to predict where defects are likely to occur and design test cases specifically targeting those areas.

Error Guessing — Common Error Checklist

Input/Data Errors:

  • Empty inputs (null strings, zero-length arrays)
  • Very large inputs (buffer overflow, integer overflow)
  • Very small inputs (division by zero, empty sets)
  • Special characters (!@#$%^&*) in text fields
  • Unicode characters in non-unicode systems
  • Leading/trailing spaces in username/password
  • Very long file names (>255 characters)

Date/Time Errors:

  • February 29 on non-leap years
  • Time zone boundaries and daylight saving transitions
  • Year 2038 problem (Unix timestamp overflow)
  • Date before 1970 or after 9999

Boundary/State Errors:

  • Performing operations in wrong order (withdraw before deposit)
  • Using system after timeout/expiration
  • Rapid repeated operations (double-click submit button)
  • Network disconnection during transaction

Security-Related Guesses:

  • SQL injection (`' OR '1'='1`)
  • Cross-site scripting (`<script>alert('xss')</script>`)
  • Path traversal (`../../../etc/passwd`)
  • Session fixation, cookie tampering

Error Guessing Strategies

  • Past Defect Analysis: Review historical defects in similar systems — what failed before?
  • Common Programming Mistakes: Off-by-one errors, uninitialized variables, resource leaks
  • Domain Knowledge: What would a malicious user do? What would an inexperienced user do?
  • Heuristics and Checklists: Maintain a personal "defect catalog" from testing experience
  • "What if?" Thinking: Systematically questioning assumptions

3.5.2 — Exploratory Testing

Exploratory Testing is a simultaneous process of test design, test execution, and learning. The tester actively explores the application, designing and executing tests on the fly based on observed behavior, without following pre-written test scripts.
📌 Exam Tip
Exploratory Testing is NOT "random testing" or "unplanned testing." It has structure — session-based test management (SBTM) is common. Key difference: In scripted testing, design and execution are separate. In exploratory, they happen together.

Characteristics of Exploratory Testing

  • Concurrent Learning, Design, and Execution: Tester learns about the system while testing it
  • No Pre-written Test Scripts: No detailed test cases before starting
  • Tester Autonomy: Tester decides what to test next based on findings
  • Documentation: After the session, test charters, notes, and defect reports are created
  • Time-boxed Sessions: Typically 60-120 minute sessions
  • Structured Approach: Uses test charters to define scope and mission

Exploratory Testing Example — E-commerce Checkout

Charter: "Explore the checkout process for an e-commerce site to find usability issues, data loss scenarios, and edge case failures."

Session (60 minutes):

  • Tester starts adding items to cart → learns that cart auto-updates without submit
  • Tester tests: add 999 items → system slows, needs pagination
  • Tester tests: apply expired promo code → error message not user-friendly
  • Tester tests: click browser back button after checkout → finds cart becomes empty unexpectedly (defect!)
  • Tester tests: switch tabs during payment → session timeout not handled properly

Findings: 7 defects found (5 not in any scripted test), 3 usability improvements suggested.

Unit 3 — Key Takeaway

Effective testing requires a balanced combination of static and dynamic techniques. Use static reviews and analysis to find defects early when they are cheap to fix. Use black box techniques to validate requirements and find functional issues. Use white box techniques to ensure thorough structural coverage of code. Use experience-based techniques to find the unexpected, creative, and subtle defects that systematic techniques might miss. The best test strategies combine all three categories based on project context, risk, and available resources.
