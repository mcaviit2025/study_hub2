Mega Project

UPI Payment System (Google Pay / PhonePe / Paytm)

🏦 Project Overview

Unified Payments Interface (UPI) is a real-time payment system developed by NPCI (National Payments Corporation of India). It allows users to transfer money instantly between bank accounts using a smartphone.

Key Features: 24/7 availability, instant transactions, QR code payments, bill payments, UPI Lite for small transactions.

Scale: Over 300 million active users, 10+ billion transactions per month, 500+ banks integrated.

Quality Criticality: One transaction failure can cause financial loss and customer trust damage.

Throughout this unit, we will understand all SQA concepts using this UPI Payment System as our mega project example.
Section 1.1

Definition of Quality, QA, QC, Difference & SQA Challenges

Quality in software means the degree to which a software product meets specified requirements and satisfies customer expectations.

1.1.1 Definition of Quality

According to ISO 9000, quality is "the degree to which a set of inherent characteristics fulfills requirements." In software, quality means:

  • Meeting customer requirements
  • Being reliable, efficient, and maintainable
  • Having minimal defects
Example from UPI Payment System

Quality in UPI means:

  • Money transfer completes within 5 seconds
  • Transaction is accurate (correct amount debited from sender, credited to receiver)
  • App does not crash during high traffic (Diwali, New Year)
  • Security: No unauthorized transactions

1.1.2 Quality Assurance (QA)

Quality Assurance (QA) is a process-oriented approach focused on preventing defects by improving development processes. QA answers: "Are we building the product correctly?"
  • Goal: Prevent defects before they occur
  • Focus: Process improvement, standards, audits, training
  • Proactive: Done throughout the development lifecycle

1.1.3 Quality Control (QC)

Quality Control (QC) is a product-oriented approach focused on identifying defects in the finished product. QC answers: "Is the product built correctly?"
  • Goal: Detect and fix defects after they occur
  • Focus: Testing, inspection, reviews
  • Reactive: Performed after product is built
Example from UPI Payment System

QA in UPI (Process-oriented):

  • Following secure coding standards for payment gateway integration
  • Conducting code reviews before merging code
  • Training developers on NPCI guidelines
  • Auditing development processes monthly

QC in UPI (Product-oriented):

  • Testing the UPI app before release (functional testing, load testing)
  • Checking if ₹100 transaction actually works
  • Finding and reporting bugs in the app
  • Testing QR code scanning functionality

Section 1.2

SQA Planning & Standards (ISO 9000)

SQA Planning is the process of defining quality goals, identifying quality activities, and creating a roadmap to achieve quality objectives. ISO 9000 is an international standard for quality management systems.

1.2.1 SQA Planning

Software Quality Assurance Plan (SQAP) is a document that outlines:

  • Quality goals and objectives
  • Quality activities to be performed
  • Roles and responsibilities
  • Standards to be followed
  • Tools and techniques to be used
  • Audit and review schedule
UPI Payment System - SQA Plan Example

SQA Plan for UPI includes:

  • Quality Goal: 99.99% transaction success rate
  • Activities: Security audits every month, load testing every quarter
  • Roles: QA Lead, Security Tester, Performance Tester
  • Standards: NPCI guidelines, ISO 27001 for security
  • Audits: Quarterly internal audits, annual external audits

1.2.2 ISO 9000 Standard

ISO 9000 is a family of standards for quality management systems. Key principles include:

  • Customer Focus: Meet customer requirements
  • Leadership: Create unity of purpose
  • Engagement of People: Involve all employees
  • Process Approach: Manage activities as processes
  • Improvement: Continuously improve
  • Evidence-based Decision Making: Use data to decide
  • Relationship Management: Manage stakeholder relationships
ISO 9000 in UPI Payment System
  • Customer Focus: UPI app tracks user satisfaction and complaints
  • Process Approach: All activities from request to response are documented
  • Improvement: After each failure, root cause analysis is done and processes improved
  • Evidence-based Decision: Transaction logs and metrics guide improvements
References
  • ISO 9001:2015 — Quality Management Systems Requirements
  • IEEE 730 — Standard for Software Quality Assurance Plans

Section 1.6

Software Reliability & Reliability Measurement Factors

Software Reliability is the probability that software will operate without failure for a specified time under specified conditions. It is a critical quality factor, especially for systems like UPI where failure has financial consequences.

1.6.1 Software Reliability (Concept Explanation)

Reliability is about trust. A reliable UPI app means:

  • You can send money anytime, and it will work
  • The transaction amount is always correct
  • The app does not crash during payment
UPI Payment System - Reliability Concept

If Google Pay has reliability of 99.99%, it means out of 10,000 transactions, only 1 transaction might fail. For 10 billion monthly transactions, 1 million transactions may fail — which is financially significant.

1.6.2 Reliability Measurement Factors

1. ROCOF (Rate of Occurrence of Failures)

ROCOF measures how frequently failures occur. It is the number of failures per unit of time or per number of transactions.
ROCOF = Number of Failures / Total Time (or Total Transactions)
UPI Example
If UPI system has 100 failures in 1,000,000 transactions → ROCOF = 100 / 1,000,000 = 0.0001 failures per transaction

2. MTTF (Mean Time To Failure)

MTTF is the average time between consecutive failures. It is used for non-repairable systems.
MTTF = Total Operating Time / Number of Failures
UPI Example
If UPI server runs for 1000 hours and fails 5 times → MTTF = 1000 / 5 = 200 hours between failures

3. MTTR (Mean Time To Repair)

MTTR is the average time taken to repair a failure once it occurs.
MTTR = Total Repair Time / Number of Repairs
UPI Example
If UPI server failure takes total 10 hours to fix over 5 failures → MTTR = 10 / 5 = 2 hours per failure

4. MTBF (Mean Time Between Failures)

MTBF is the average time between failures, including both operating time and repair time. MTBF = MTTF + MTTR
MTBF = Total Time (Operating + Repair) / Number of Failures
UPI Example
If MTTF = 200 hours, MTTR = 2 hours → MTBF = 200 + 2 = 202 hours between failures

5. POFOD (Probability of Failure on Demand)

POFOD is the probability that the system will fail when a service is requested.
POFOD = Number of Failed Demands / Total Number of Demands
UPI Example
If out of 1,000,000 payment requests, 10 fail → POFOD = 10 / 1,000,000 = 0.00001 (1 in 100,000 requests fails)

6. Availability

Availability is the proportion of time the system is operational and accessible when needed.
Availability = MTTF / (MTTF + MTTR) = Uptime / (Uptime + Downtime)
UPI Example
If MTTF = 200 hours, MTTR = 2 hours → Availability = 200 / 202 = 0.9901 = 99.01%
For critical systems like UPI, target Availability is 99.99% (Four nines) or higher.
99.99% Availability = Only 52 minutes of downtime per year!

Exam Tip

Remember the difference:
• MTTF = Time until failure (for non-repairable systems)
• MTBF = Time between failures (includes repair time)
• MTTR = Time to fix after failure
• For UPI (repairable system), MTBF is more relevant than MTTF.
