Topic 4.1

Test Organization: Roles & Skills of Tester, Test Lead, Test Manager

Test Organization defines the structure, roles, responsibilities, and reporting relationships within the testing team. A well-organized testing team has clearly defined roles with appropriate skills and career progression paths.
📌 Last Night Tip
Remember the hierarchy: Test Manager (strategic, people management, budget) → Test Lead (tactical, daily coordination, technical guidance) → Tester (execution, test case creation, defect reporting).

Testing Team Structure — Hierarchical Organization

Fig 4.1 — Testing Team Hierarchy

Detailed Role Descriptions

👤 Tester (Test Engineer)

Definition: The individual who executes test cases, reports defects, and verifies fixes. The tester is the hands-on executor of the test plan.

Key Responsibilities:

  • Review and analyze requirements, user stories, and specifications
  • Design, write, and maintain test cases and test data
  • Set up and configure test environments
  • Execute test cases (manual and automated)
  • Log defects with clear, reproducible steps
  • Retest fixed defects (confirmation testing)
  • Perform regression testing after fixes
  • Participate in reviews and walkthroughs
  • Provide test execution status updates

👔 Test Lead

Definition: The individual who coordinates testing activities, guides the test team, and ensures testing follows the plan. Reports to Test Manager.

Key Responsibilities:

  • Lead and mentor a team of testers (typically 3-10 people)
  • Assign test tasks and monitor progress
  • Review test cases and provide technical guidance
  • Coordinate with developers, business analysts, and project managers
  • Track test execution metrics and report to Test Manager
  • Manage test environment and tool access
  • Conduct defect triage meetings
  • Prepare test summary reports
  • Onboard and train new testers

🎯 Test Manager

Definition: The individual responsible for overall test strategy, planning, resource allocation, budget, and stakeholder communication across one or more projects.

Key Responsibilities:

  • Define test strategy, policies, and standards for organization
  • Create and manage test budgets and resource allocation
  • Hire, train, and evaluate testing staff
  • Develop and maintain test plans for projects
  • Manage relationships with stakeholders (clients, senior management)
  • Establish test metrics and quality dashboards
  • Decide on test automation strategy and tool investments
  • Manage vendor relationships for outsourced testing
  • Ensure compliance with industry standards (ISO, CMMI, etc.)
  • Present test progress and release recommendations to leadership

Topic 4.2

Test Planning — Test Plan as per IEEE 829 Standard

Test Planning is the activity of defining the test strategy, scope, resources, schedule, and approach for testing. The IEEE 829-2008 Standard for Software Test Documentation provides a comprehensive template for creating a Master Test Plan (MTP).
📌 Exam Tip
IEEE 829 Test Plan has 14-17 sections depending on version. Memorize the KEY sections: Test Plan Identifier, Introduction, Test Items, Features to be Tested, Features NOT to be Tested, Approach, Pass/Fail Criteria, Suspension/Resumption Criteria, Test Deliverables, Environment, Schedule, Risks, Staffing.

IEEE 829 Master Test Plan Template — Complete Structure

Fig 4.2 — IEEE 829 Test Plan Document Structure

Detailed Description of Each Test Plan Section

SectionDescriptionExample Content
1. Test Plan Identifier Unique identifier for version control and traceability "TP-MCA-ONLINEBANKING-V1.0"
2. Introduction Project background, objectives, scope, and references "Objective: Validate online banking system for SBI before March 2025 release"
3. Test Items List of items being tested (code modules, APIs, databases) "Login module, Fund Transfer API, Transaction History, Balance Inquiry"
4. Features to be Tested Specific functionalities that will be tested "User authentication, fund transfer validation, transaction history retrieval, statement generation"
5. Features NOT to be Tested Explicit exclusions with justification "Biometric login (deferred to Phase 2), Bill payments (third-party API not ready)"
6. Approach Testing techniques, levels, types, and tools "Black-box (EP, BVA) for functional testing. Selenium for automation. JMeter for load testing. Manual exploratory for UI."
7. Pass/Fail Criteria Conditions for test case/pass or overall release "Pass: All critical tests pass. Fail: Any critical defect remains open. Release: ≥98% pass rate, no severity 1 defects."
8. Suspension/Resumption When to pause testing and conditions to restart "Suspend if environment unstable >2 hours. Resumewhen environment restored and smoke test passes."
9. Test Deliverables Documents and artifacts produced during testing "Test Plan, Test Cases, Test Logs, Defect Reports, Test Summary Report, Automation Scripts"
10. Test Environment Hardware, software, network, and tools required "2 Windows servers, 1 DB server, 10 test clients, Chrome/Firefox, JIRA, Selenium Grid"
11. Test Schedule Timeline with milestones and activities "Week 1: Plan → Week 2-3: Case design → Week 4-5: Execution → Week 6: Regression & closure"
12. Risks & Contingencies Potential issues and mitigation plans "Risk: Developer delays → Mitigation: Shift-left testing, early static analysis. Risk: Environment unavailability → Mitigation: Backup environment on cloud."
13. Staffing & Training Team composition and required training "1 Test Lead, 4 Testers. Training needed: Selenium (2 days), Domain (1 day)."
14. Approvals Sign-off authorities and dates "Approved by: Test Manager, Project Manager, QA Director. Date: 15-Jan-2024"

Topic 4.3

Test Process Monitoring & Control

Test Monitoring involves tracking and reporting test progress against the plan. Test Control involves taking corrective actions when monitoring shows significant deviations from the plan. Both are essential for managing test projects successfully.
📌 Last Night Tip
Monitoring = Tracking, Measuring, Reporting. Control = Correcting, Replanning, Adjusting. You monitor metrics (logs, defect density), then control by adjusting resources, schedule, or scope.

Defect Density Metric

Defect Density measures the number of defects per unit of software size (e.g., per KLOC — thousand lines of code, per function point, per module). It is used to assess software quality and predict remaining defects.

📊 Defect Density = (Number of Defects Confirmed) / (Size of Software Module)
Defect Density Calculation Example

Scenario: A payment processing module has 15,000 lines of code (15 KLOC). Testers found 45 defects during testing.

Defect Density = 45 / 15 = 3 defects per KLOC

Industry Benchmarks:

  • Excellent: < 1 defect/KLOC
  • Good: 1-3 defects/KLOC
  • Average: 3-7 defects/KLOC
  • Poor: 7-15 defects/KLOC
  • Critical: > 15 defects/KLOC

Use Case: The payment module at 3 defects/KLOC is "Good" quality. Modules with >7 defects/KLOC should be prioritized for refactoring and additional testing.

4.3.3 — Test Control

Test Control involves taking corrective actions based on test monitoring data to bring testing activities back in line with the test plan or to adjust the plan when deviations are unavoidable.

Test Control Actions — Examples

Monitoring FindingTest Control Action
Test execution is falling behind schedule • Add overtime or additional testers
• Reduce test scope for low-risk features
• Prioritize critical tests
• Automate repetitive tests
Defect density is higher than expected • Request developers to perform additional unit testing
• Increase testing in high-defect modules
• Conduct root cause analysis
• Enhance static analysis and code reviews
Environment is unstable/offline frequently • Escalate to operations team
• Request dedicated test environment
• Schedule environment maintenance windows
• Use backup/cloud environment
Test cases have low defect detection rate • Review and enhance test case design
• Add exploratory testing sessions
• Use different test design techniques
• Involve domain experts
Regression testing time exceeds window • Prioritize regression test suite (critical paths only)
• Parallelize execution across multiple machines
• Automate additional regression tests

Topic 4.4

Test Scenario, Test Suite, Test Cases (Positive & Negative)

Test Scenarios are high-level descriptions of what to test. Test Cases are detailed step-by-step instructions with inputs and expected results. Test Suites are collections of test cases grouped by functionality or priority. Positive test cases verify expected behavior; negative test cases verify error handling.
📌 Exam Tip
Hierarchy: Test Scenario (What to test? One line) → Test Case (How to test? Detailed steps) → Test Suite (Collection of test cases). Positive test cases follow happy path; Negative test cases test invalid inputs and error conditions.

Hierarchy of Test Artifacts

Fig 4.6 — Test Scenario → Test Case → Test Suite Hierarchy

Test Scenario

Definition: A test scenario is a high-level description of a functionality or feature to be tested. It answers "What needs to be tested?" without specifying the exact steps.

Test Scenario Examples (E-commerce Application)
  • TS-001: Verify user registration functionality
  • TS-002: Verify user login functionality
  • TS-003: Verify product search functionality
  • TS-004: Verify add to cart functionality
  • TS-005: Verify checkout and payment functionality
  • TS-006: Verify order cancellation functionality

IEEE 829 Test Case Specification Template

Fig 4.7 — IEEE 829 Test Case Specification Template

Positive vs Negative Test Cases

✅ POSITIVE TEST CASES

Definition: Test cases that use valid inputs and expected behavior to verify that the system performs its intended functions correctly.

Purpose: Confirm that the software works as specified in the requirements.

Example (Login):

  • Valid username + valid password → Login successful
  • Registered user with correct credentials → Dashboard displayed
  • Remember me checkbox → Session persists across browser close

Key characteristic: All inputs are valid, all preconditions met, expected outcome is SUCCESS.

❌ NEGATIVE TEST CASES

Definition: Test cases that use invalid inputs, unexpected conditions, or error scenarios to verify that the system handles failures gracefully.

Purpose: Validate error handling, validation logic, and system robustness.

Example (Login):

  • Invalid username + valid password → Error message displayed
  • Valid username + invalid password → "Invalid credentials" message
  • Empty username + valid password → Validation error
  • SQL injection in username field → Not executed, proper sanitization
  • XSS script in username → Properly escaped, not executed
  • Account locked after 3 failed attempts → Lockout message displayed

Key characteristic: At least one input is invalid or precondition is violated, expected outcome is ERROR HANDLING (not crash).

Topic 4.5

Configuration Management — Configuration Management Support for Testing

Configuration Management (CM) is the discipline of identifying, controlling, and tracking changes to software artifacts throughout the development lifecycle. For testing, CM ensures that testers know exactly what version of the software they are testing, what test artifacts are current, and what changes have been made.
📌 Last Night Tip
CM answers: WHAT version are we testing? WHAT test cases are current? WHO changed WHAT and WHEN? Without CM, testing is chaotic — you might test old code, use outdated test cases, or miss critical changes.

Key Configuration Management Activities for Testing

📌

Configuration Identification

Unique identification of all test artifacts:

  • Test Plan versions (v1.0, v1.1, v2.0)
  • Test Case versions (TC-LOGIN-001_v3)
  • Test Data versions
  • Test Script versions (automation)
  • Test Environment configurations
🔒

Configuration Control

Controlled change management:

  • Check-in/Check-out of test artifacts
  • Change request approval process
  • Version control systems (Git, SVN)
  • Baseline creation for releases
  • Access control and permissions
📊

Configuration Status Accounting

Tracking and reporting:

  • What versions are in test?
  • What changes were made?
  • Who made each change?
  • When was each change made?
  • Status of test artifacts
Fig 4.8 — Configuration Management in Testing Lifecycle

Why Configuration Management is Critical for Testing

  • Reproducibility: If a defect is found, you need to know exactly which version of code and test cases produced it
  • Traceability: Link test cases to requirements and code changes
  • Regression Testing: Know which test cases need to be re-run after changes
  • Audit Compliance: Regulatory requirements (FDA, ISO, banking) demand CM
  • Collaboration: Multiple testers can work without overwriting each other's work
  • Environment Consistency: Test environment configuration must match production

Topic 4.6

Risk and Testing — Project Risk & Product Risk

Risk-based testing prioritizes testing activities based on the level of risk associated with different features or components. Risks are potential future problems that could negatively impact project success (project risks) or product quality (product risks).
📌 Exam Tip
Product Risk = Risk to PRODUCT QUALITY (e.g., payment failure, data loss, security breach). Project Risk = Risk to PROJECT SUCCESS (e.g., budget overrun, schedule delay, resource shortage). Both affect testing priorities.

Types of Risks in Testing

📦 PRODUCT RISK

Definition: Risk that the software product will fail to meet quality requirements or user expectations.

Examples:

  • Payment gateway integration fails → Financial loss
  • Security vulnerability (SQL injection) → Data breach
  • Performance degradation under load → Poor user experience
  • Data corruption during backup → Permanent data loss
  • Incorrect calculation in tax module → Legal compliance issue
  • UI usability issues → Low customer adoption
  • Integration failure with third-party API → Broken feature

Testing Focus: High-risk product areas receive more testing (more test cases, higher coverage, more techniques).

📋 PROJECT RISK

Definition: Risk that the project will fail to meet schedule, budget, or resource constraints.

Examples:

  • Schedule slippage → Release delayed
  • Budget overrun → Testing cut short
  • Staff shortage → Insufficient testing coverage
  • Environment unavailability → Testing blocked
  • Tool/technology failure → Automation impacted
  • Poor requirement quality → Ambiguous test objectives
  • Vendor dependency → Third-party delays
  • Communication gaps → Missed requirements

Testing Focus: Mitigation strategies (contingency plans, early start, scope reduction, outsourcing).

Topic 4.7

Incident / Defect Management

Incident/Defect Management is the process of identifying, logging, tracking, analyzing, and resolving defects or incidents found during testing. An effective defect management process ensures that no defect is forgotten and that quality improves over time.

4.7.1 — Defect Life Cycle

Fig 4.10 — Defect Life Cycle (Bug Life Cycle)

Defect Life Cycle States — Detailed Explanation

StateDescriptionResponsible
NEW Defect is first logged by tester. No action taken yet. Tester
ASSIGNED Defect is reviewed and assigned to a developer for analysis. Test Lead / Manager
OPEN Developer accepts the defect and starts working on fix. Developer
FIXED Developer has made code changes to resolve the defect. Developer
REJECTED Defect is not valid — either user error, cannot reproduce, or intended behavior. Developer / Lead
DUPLICATE Same defect has already been reported by another tester. Triage Team
REOPENED Tester verified fix but issue still exists or fix introduced new problem. Tester
CLOSED Fix is verified working, no further action needed. Tester

   - Product search (covered in separate test plan)
   - Returns/Refunds (Phase 3)

2. RISK ASSESSMENT:
   High Risk Features (Intensive testing):
   - Payment gateway integration (financial impact)
   - Price calculation with coupons (revenue impact)
   
   Medium Risk Features:
   - Address validation (user experience)
   - Order confirmation (customer communication)
   
   Low Risk Features:
   - UI layout
   - Confirmation email formatting

3. TEST APPROACH:
   Functional Testing (Black Box):
   - Equivalence Partitioning: Cart subtotal ranges (₹0-500, ₹501-2000, ₹2001+)
   - Boundary Value Analysis: Minimum order (₹100), Free shipping threshold (₹999)
   - Decision Table: Coupon combinations (10% off vs Free Shipping)
   
   Integration Testing:
   - Payment gateway API integration
   - Inventory system stock update after order
   - Email service confirmation delivery
   
   Performance Testing:
   - 500 concurrent users during checkout
   - 95% transactions completed within 3 seconds
   
   Security Testing:
   - Payment information encryption
   - No storage of CVV
   - Session timeout during checkout

4. TEST SCHEDULE (10 days):
   Days 1-2: Test case design (60 positive, 40 negative cases)
   Days 3-5: Functional test execution
   Days 6-7: Integration and security testing
   Days 8-9: Regression testing
   Day 10: Defect verification and closure

5. RESOURCES:
   - 1 Test Lead
   - 3 Testers (2 functional, 1 automation)
   - Staging environment with test payment gateway
   - Selenium for automation (critical paths only)

Unit 4 — Key Takeaway

Test management is the discipline that transforms testing from an ad-hoc activity into a controlled, measurable, and improvable process. The key pillars are: clear roles and responsibilities (Tester, Test Lead, Test Manager), comprehensive planning (IEEE 829 Test Plan), monitoring through metrics and logs (Defect Density, Test Logs, Test Summary Reports), structured test artifacts (Scenarios, Cases, Suites), configuration management for traceability, risk-based prioritization, and formal defect management with clear life cycle. The case studies demonstrate how these concepts apply to real applications — from e-commerce checkout to banking transfers to API testing.
